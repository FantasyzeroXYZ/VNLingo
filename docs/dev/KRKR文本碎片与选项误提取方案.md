# 1. 问题与实测证据

## 1.1 用户报告的现象

| 编号 | 现象 |
|---|---|
| P1 | 提取到的文本**不够准确**，经常只是片段单词 |
| P2 | 提取到的文本**大量重复** |
| P3 | 提取到的**似乎是选项文本**，而**对白文本没有准确更新** |

## 1.2 现场前提：当时生效的只有字形通道

设备 `shared_prefs/*.xml` 中 **`kr_extract_probe` 与 `kr_extract_tjs` 两个键都不存在**
（即均为默认 `false`，见 [EngineSettingsStore.kt:467](../../app/src/main/java/com/tyranor/next/core/settings/EngineSettingsStore.kt#L467)
与 [EngineSettingsStore.kt:36](../../app/src/main/java/com/tyranor/next/core/settings/EngineSettingsStore.kt#L36)）。
全量 logcat 中**没有任何 `[TNEXT]` 行**。

结论：解析器包装通道（`TYRANOR_NEXT_KRKR_EXTRACT_WRAP_V4`，提交 `c633a8e`）**当时没有运行**；
用户看到的所有文本都来自 **FT 字形通道 + `Label::setString` 虚表通道**。

## 1.3 FT 通道原始流（未做任何重建的码点链）

真机 13:18 - 13:31，`KrkrExtract: ft raw` 实测（原样摘录）：

## 1.4 字形通道空闲期冻结

```
13:30:14 → 13:31:12（约 1 分钟，每 2s 一条）

```

`idx_calls` / `glyph_calls` 完全不变 —— 说明**对白推进期间一次字形请求都没有发生**。

## 1.5 词典层旁证：提取出来的「句子」本身就是碎片

同期 `DiagLog`（设备 `files/diag/diag.log`）中的查词命中：

```

[10-08 13:29:25.602 dict] hit: はかず groups=5 in 25ms
[10-08 13:29:27.418 dict] hit: かず groups=2 in 22ms
```

更早的会话同样是单字命中（`か` / `が` / `れ` / `い` / `づ`）。即面板里的「句栏」内容
本身就只有一到三个字，与 P1 的「片段单词」一致。

# 2. 根因分析

三条现象分别对应三层不同的成因，必须分开处理。

## 2.1 R1：字形通道只能看到「图集未命中的字形」（P1 + P3 的根因）

`FT_Get_Char_Index` / `FT_Load_Glyph` 只在**字形需要被请求**时命中，
即**字体图集缓存未命中**的那一次。据此推断画面元素的可提取性：

| 画面元素 | 字形请求行为 | 提取结果 |
|---|---|---|
| 选项按钮（出现即整块新建/重绘，每项首次绘制） | 全部字符都是图集未命中 | **整行被捕获** |
| 对白文本框（打字机逐字推进、Label 复用、常用字形已在图集） | 多数字符缓存命中，仅零星触发 | 片段、长时间不更新 |
| 字体图集 / 对话窗装饰 | 整批字形请求 | 产生 `HVIFNWYqO幅モトヤダタ゛…` 这类噪声串 |

这同时解释了 P1（碎片）与 P3（只在选项处更新、对白不更新）：
**该通道看的是「字形缓存事件」，与「哪段是正文」无关**；
凡「新绘制」的文本必然被捕获，凡「缓存命中的增量重绘」必然看不见。

对照：kazurauta（葛唄）在同一通道下工作正常，是因为其正文每字都重新走字形请求
（并行会话实测 `idx/glyph` 168 → 909 持续增长）。**这是「部分游戏可用」的兜底通道，
不是通用方案。**

## 2.2 R2：页推导只能靠「最长重复后缀」猜（P2 的根因）

`ftDerivePage` 的做法是在原始码点链里找**最长的重复后缀**，把它当作「倒数第二份整窗快照」，
再补末尾增量（见 [krkr_extract_hook.cpp:461-483](../../engine/src/main/cpp/krkr_extract_hook.cpp#L461)）。
打字机每加一字整行重绘，链 = `『き『きさ『きさら…` 这种前缀链，靠「重复后缀」猜本就不稳：

- 猜对 → 得到整页；
- 猜错 → 得到 `きさらぎさらぎさらぎさらぎきさらぎれいれい` 这类**堆叠**；
- 链只有一份快照（一次性整页绘制）→ `ftDerivePage` 返回空，永不上行。

`known=409` 长时间不变，正是「链再也推不出新页」的表现。

## 2.3 R3：解析器包装通道的 tag 语义与 KAGParserEx 不匹配（真正的解法当前不可用）

现行探针脚本 `krExtractProbeScript()`（[EngineLauncher.kt:1584-1679](../../app/src/main/java/com/tyranor/next/core/game/launch/EngineLauncher.kt#L1584)）
与发射器 v8（[EngineLauncher.kt:1695-1726](../../app/src/main/java/com/tyranor/next/core/game/launch/EngineLauncher.kt#L1695)）
的重建规则是一致的：

```
if (tagname == "ch") tnBuf += d.text;      // 只认 ch 标签、只读 d.text
else { if (tagname == "r") tnBuf += " ";  tnEmit(tnBuf); }   // 其它任何标签即冲刷
```

该规则对 **KAGParser**（KAG3 经典解析器）成立：`ch` 标签逐字给出正文。
但 tsukikage 使用 **KAGParserEx 变体**，其 tag 流形态不同，于是：

- 正文可能**不叫 `ch`**，或文本**不在 `d.text` 字段** → 缓冲收不到正文；
- 只有恰好被判为 `ch` 的零散 tag 被累积 → `のものもの`、`せいちせいちせいち` 这种重复形态；
- `tnEmit` 在**每个其它 tag** 触发 → 碎片化（并行会话记录：推进 10 次只到 1 条）。

并行会话的提交 `c633a8e` 已证明的是「hook 点可行、游戏不崩、通道可达」，
**没有解决文本重建**；且该通道默认关闭，实际运行时并未生效。

# 3. 类型判定：提取到的到底是不是选项

用户观察与 §2.1 的推断完全一致，但**目前尚无直接对照证据**（原文未能解出）。
因此本方案把「类型判定」列为必须取证的项，而不是既定结论。

取证手段（见 §4.1）：把解析器层 tag 流打出来，在**有选项的分支**与**普通对白处**
各推一次，比较 tag 名与文本长度分布；同时在 FT 通道打印「每次命中时的字形计数与
首字码点」，用于判断命中是否集中在选项出现的时刻。

判定表：

| 观察 | 结论 |
|---|---|
| 选项处出现成组的短 tag（每项一行），对白处出现长 `ch` 序列 | 选项走独立 tag 形态，需在重建时区分并默认丢弃 |
| 选项与对白 tag 形态相同、仅出现时机不同 | 需要按「对白文本框」上下文判定（见 §4.3 的过滤策略） |
| FT 命中时刻与选项出现高度相关 | 证实 §2.1「新绘制才可见」的机制 |

# 4. 改动点

## 4.1 P0：解析器层 tag 取证（零风险，先做）

**目标**：拿到 KAGParserEx 真实 tag 形态，作为重建逻辑的唯一依据。

**做法**：升级 `krExtractProbeScript()` 为「取证版」（仍只在 `kr_extract_probe`
开启时注入、不替换任何类、不改变游戏行为）：

1. 在包装类的 `getNextTag()` 内，对**前 64 个 tag** 记录：
   - `tagname` 的**十六进制**（逐字符 `%02x`，例如 `ch` → `"6368"`）；
   - `d.text` 的**长度**与**首字符码点**（`d.text.charAt(0)` 的码点值，十进制即可）；
   - 是否存在 `d.elm`（KAG 标签属性容器）及其非空判断；
2. 通过 `Debug.message("[probe] tag=<hex> len=<n> cp=<code> elm=<0|1>")` 输出，
   与既有探针同一通道（logcat tag `cocos2d-x debug info`）；
3. **纯 ASCII 硬约束**：`patch.tjs` 追加内容只能含 ASCII
   （Kirikiroid2 按内容探测 `patch.tjs` 编码，混入 UTF-8 日文会毁掉后续 SJIS 脚本解码）
   —— 所以**绝不可**直接打印日文 tag 文本，只能打十六进制与长度；
4. tag 数量达到 64 条后自动停止打印，避免刷屏（历史教训：异常路径单次可打约 2 万行日志）。

**验收**：logcat 中出现 64 行 `[probe] tag=...`，可据此还原 tag 名与文本长度分布。

## 4.2 P0：字形通道加过滤与降级（让面板不再被污染）

**目标**：在解析器通道可用之前，字形通道不产出与画面正文无关的内容。

改动点（[krkr_extract_hook.cpp](../../engine/src/main/cpp/krkr_extract_hook.cpp)）：

1. **非对白过滤**：对 `gRawBuf` 派生出的候选加判定——
   - 单次派生结果长度低于阈值（建议 < 4 个码点）不上行；
   - 与「同页内已上行内容」完全重复时不上行（现只有 `gLastEmitted` 一位，扩为同页集合）；
   - 连续 N 次（建议 3）派生结果相同 → 判定为冻结，不再重复上行。
2. **冻结提示**：`ft state` 中 `idx_calls` / `glyph_calls` 连续 ≥5s 无增长且
   `gPage` 非空时，通过既有诊断通道标记「glyph-frozen」，供面板显示降级状态。
3. **保留原设计**：锁内只做快照拷贝、推导在锁外、400ms 轮询等防 ANR 设计不得破坏；
   新增判定必须在锁内只做 O(1) 比较，重运算一律移出锁。

**验收**：`きさらぎさらぎ…` 这类堆叠与装饰串不再出现在面板句栏；
kazurauta 回归正常（既有 `ft line` 输出不变）。

## 4.3 P1：按取证结果重写重建逻辑（解析器通道）

依据 §4.1 的 tag 实证，重写 `krExtractProbeScript()` 的包装类：

1. **正文 tag 识别**：按实证的 tag 名与字段取值（可能不是 `d.text`）；
2. **打字机语义**：同一轮的重复回放（前缀链）不得重复追加——
   用「新段是否为已缓冲内容的重复前缀」判定，是则替换而非追加；
3. **整句边界**：由实证确定（可能是 `ch` 连续段 + 等待/换行标签），
   在边界处一次性 flush，避免逐 tag 冲刷造成的碎片；
4. **选项区分**：若实证显示选项走可区分的 tag 形态，则在重建时**默认丢弃**选项文本
   （或标记为候选但不进句栏主位）；
5. **失败可回滚**：所有逻辑 try/catch 包裹；出现异常立即停用包装并回落到原类，
   不得影响游戏运行。

**验收**：推进一句对白 → 面板句栏出现与画面一致的**整句**；DiagLog 出现整词命中
（如 `きさらぎ` / `かずは` 这类完整词）而非单字；选项出现时句栏不被选项文本替换。

## 4.4 P2：开关接线（与既有方案 §4.1 合并实施）

`kr_extract_probe` / `kr_extract_tjs` / 三个引擎的提取钩子全局开关目前**都没有 UI 入口**
（setter 零调用方）。取证与重写阶段若要反复开关，需要：
- 设置页「文本提取」分区（ONS / KRKR / Artemis 三个钩子开关 + KRKR 文本输出方式）；
- 避免 `ctx as Activity` 强转（历史闪退根因），统一 `AppLocaleController.findActivity(ctx)`；
- 三 locale 文案同步。

# 9. 与既有方案的冲突说明（重要）

**同时修正 §9 的表述**（对第二轮文档自身的更正）：§6.5.7 记录的
「包装后提取桥收到 `せいちせいちせいち` / `のものもの`」**也是误判**——那两条同样来自
FT 字形通道（`NativeBridge.onKrkrText` 对 `[FTLN]` 与 `[TNEXT]` 打同一条日志，无法区分）。
本轮加入 `wrapCtor` / `gt` 计数后可以确定：**解析器包装通道对 tsukikage 从未生效**，
「换类瞬间包装」对本游戏类（KAGParserEx）**不是可行路线**，而不是「重建逻辑待完善」。

由此 B3（按 tag 实证重写重建逻辑）**失去前提**：没有可达的 tag 观测点就无法取证，
也就无法按实证重写。剩余可选路线只有内核级（krkr2-main 源码钩子）或从游戏脚本侧
（`Config.tjs`/`TextTagConverter.tjs` 等，但该游戏 XP3 被 PackinOne 类插件加密，
本轮未解出）另找入口。

## 10.2 B2 字形通道过滤与降级（已完成并验证）

`krkr_extract_hook.cpp` 落地三条过滤 + 一个降级标记，均在锁内只做 O(1)/短串比较，
保持原有「400ms 轮询 + 512B 快照 + 推导在锁外」的防 ANR 设计：

1. **长度下限**：派生页 < 4 个码点不上行（去掉单字/双字碎片）；
2. **同页去重**：最近 8 条已上行内容组成环形集合，重复内容不再上行
   （原实现只有一位 `gLastEmitted`）；
3. **堆叠串判定**：串首同一 1..3 码点单元连续重复 ≥3 次即判定为
   `きさらぎさらぎさらぎさらぎ…`、`か　ず　はか　ず　は…` 这类重绘链产物，不上行；
4. **冻结降级标记**：`idx_calls/glyph_calls` 连续 ≥10s 无增长时打
   `glyph-frozen: no FT request for 10s (font atlas hit)`，供面板/日志判定
   「该通道此刻看不到对白推进」。

**踩坑（本方案自身的错误设计，已修）**：最初按 §4.2 写了
「派生结果连续 N 次相同 → 判定冻结 → 停发」，实测**误杀正常对白**——打字机停顿时
派生结果与 raw 都不变，而这正是该上行的时刻（kazurauta 因此从 10 条掉到 **0 条**
`ft line`）。修正：冻结只做诊断，不参与上行门控；真正防重复由 `gPage != gLastEmitted`
与同页去重承担。

**验证（真机）**：

| 场景 | 结果 |
|---|---|
| kazurauta 回归 | 正常：10 条 `ft line`，内容为完整句（「ねえねえ！　あれ見て！」、`キッチンカーではタピオカミルクティーが大人気。`…），无重复、无堆叠 |
| tsukikage 过滤前（用户报告期） | 4 条碎片 + `きさらぎさらぎさらぎさらぎきさらぎれいれい` 这类堆叠串进句栏 |
| tsukikage 过滤后（本轮） | **仅 1 条**「のものもの」，堆叠/装饰串不再上行；同时打 `glyph-frozen` 标记 |

# 11. 结论与后续

- 本方案的核心假设「换类瞬间包装能拿到 tag 流」**对 tsukikage 不成立**（§10.1 硬证据）；
  该结论只针对「不使用 `global.KAGParser` 构造解析器」的游戏类，其它 KRKR 游戏仍需实测。
- 字形通道已按 §4.2 完成过滤，**不再是句栏污染源**，但它对这类游戏**天生不完整**
  （只能看到图集未命中的字形），不能作为主通道。
- 真正可用的通道仍是内核级（krkr2-main 源码钩子），或找到游戏脚本里真正的解析器入口；
  两者都超出本方案范围，记入待办。
