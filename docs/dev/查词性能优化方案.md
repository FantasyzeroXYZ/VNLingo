# 1. 结论

查词慢的根因不是词形还原算法，也不是 SQL 语句本身，而是：

**`entries` 表没有 `reading` 索引，而面板查词对每个候选都发一次 reading 查询 ——
每个这样的查询都退化为「按 `dict_id` 单列索引顺序扫描 + `ORDER BY pop DESC`
临时 B 树排序」。**

真机实测（红米 K40，Android 11，SQLite 3.28.0，设备上真实词典 6.7 万词条）：

| 场景 | 当前 schema（无 reading 索引） | 补 `(reading, dict_id)` 索引 |
|---|---|---|
| 面板逐字扫描整句（scanByChar，句一） | 2345 ms | 22.7 ms |
| 面板逐字扫描整句（句二） | 2521 ms | 19.5 ms |
| 词典页搜索 search()（句一） | 7.4 ms | 8.1 ms |
| searchTermWithDeinflect（かえした） | 1.41 ms | 1.05 ms |
| 50 万词条 · 面板逐字扫描 | 46379 ms | 25.6 ms |
| 50 万词条 · reading=? 单次查询 | 71 ms | 0.011 ms |

即：**面板单次点选查询 2.3 秒，补索引后 23 毫秒（约 100 倍）**；词典规模越大差距越大。

# 3. 根因分析

## 3.1 面板路径：每个候选一次 reading 查询

`OnsExtractPanel.tryMatchCandidate`（约 1332 行）对**每个候选**依次做：

1. `searchTermExact(cand)` —— 走 `(dict_id, term)` 索引，0.17 ms，正常；
2. `searchReadingExact(cand)`（候选含假名时）—— **退化扫描**；
3. 对每个词形还原候选重复 ① 与 ②。

`scanByChar`（约 1357 行）从整句全长逐层递减，整句未命中时要跑满所有层：
一个 21 字符句子约 63 个候选，乘上还原候选后累计 200 - 600 次查询。
按无索引时每次 4 ms（6.7 万词条）到 70 ms（50 万词条）计，即 1 - 40 秒。

## 3.2 词典页路径为何相对不慢

`DictionaryScreen` 的搜索走 `searchTermWithDeinflect` → 未命中再退 `search()`；
`search()` 对每层前缀同样会查 reading，但层数是「查询串长度」且命中即返回，
21 字整句实测 7.4 ms（无索引）—— 慢的是**板载逐候选扫描的次数**，不是单次查询。

## 3.3 次要开销（索引修好后仍存在）

- `buildScope()` 每次查询都重跑一条 `dicts` 子查询（0.086 ms/次 × 数百次）；
- 逐候选串行发查询，每次都有游标/JNI 往返（约 0.2 ms/次）；
- SQLite 页缓存为默认值（约 2 MB），大词典下索引页与数据页频繁换出；
- 主进程（词典页导入/删除）与引擎进程（游戏内查词）共用同一库文件，
  当前为回滚日志模式（库目录可见 `-journal`），跨进程写会互相阻塞。

# 4. 与 TrackReader 的实现差异

参考实现位于 `D:\code\test-JavaScript\TrackReader\packages\domain\src\yomitan`
（`db.ts`、`dictionary-query.ts`、`dictionary-import.ts`、`dictionary-store.ts`）。

| 维度 | TrackReader | VNLingo 现状 | 影响 |
|---|---|---|---|
| 索引定义 | `db.ts` 对词条表同时建 `term`、`reading`、`dictionaryId` 三个索引 | `OnsDictStore.migrate()` 只建 `term`（单列，实际未用）与 `(dict_id, term)`，**无 reading 索引** | 面板 reading 查询退化为扫描，2.3 s vs 23 ms |
| 批量查询 | `batchSearchTerms()` 在一个事务内对全部候选并发查 `term` + `reading` 两个索引，再按词条分组 | 逐候选串行发查询，无批量化 | 索引到位后仍有数百次往返 |
| reading 查询条件 | `skipReading = currentScope !== 'ja'`，非日语一律不查读音 | `hasKana(cand)` 判定；CJK 逐字扫描中只要候选含假名就查 reading | 查询量被放大 |
| 词典范围过滤 | `processRawResults` 用词典元数据（含 scope/优先级）过滤，元数据常驻内存 | `buildScope()` 每次查询现查数据库 | 0.086 ms/次 × 数百次 |
| 词形还原粒度 | CJK 每候选一次；非 CJK 首词只还原一次再组「冲锋车」两阶段扫描 | 两阶段思路已移植（`scanByWordTwoPhase`），CJK 每候选 re-deinflect | 合计仅 0.4 ms/句，可忽略 |
| 查表还原 | `tableLookup`（语言包反查表）优先于规则还原 | 未移植（仅规则还原） | 功能差异，非性能 |
| 词形还原规则数据 | ja 全量、zh/vi 无 transforms（仅预处理） | 已同步导出五语言 JSON；zh/vi 同为无 transforms | 无缺口 |
| 查询结果缓存 | 无 | 无 | 重复点选同一句时可优化 |

补充：应用侧 schema 与 TrackReader 的差异不只影响速度 —— 索引缺口在
`migrate()` 中补建即可，不需重新导入词典（详见 §5.1）。

# 5. 优化方案

## 5.1 P0：补 `(reading, dict_id)` 索引

改动点：`OnsDictStore.migrate()`，在既有 `idx_entries_dict_term` 之后追加：

```java
database.execSQL("CREATE INDEX IF NOT EXISTS idx_entries_reading ON entries(reading, dict_id)");
```

- 生效方式：`migrate()` 在每次 `db()` 打开时执行，**老用户启动即自动补建**，
  无需重新导入词典；
- 代价：首次启动多一次建索引（6.7 万词条约 0.2 s，50 万词条数秒）——
  建议放到 `init()` 的后台线程，或导入流程结束后立即建立并给进度提示；
- 预期：面板扫描 2345 ms → 约 23 ms；50 万词条 46379 ms → 约 26 ms；
- 风险：低。附带收益：可删除实际未被使用的单列 `idx_entries_term`（`term = ?`
  已被 `(dict_id, term)` 覆盖），节省库体积。

## 5.2 P0：导入后执行 `ANALYZE`

改动点：`importFromFile()` 成功收尾时执行一次 `database.execSQL("ANALYZE")`。

- 动机：当前库内 `sqlite_stat1` 为空，查询规划器没有统计信息可依据（现网
  计划选择是「碰巧」正确）；
- 预期：多词典 `IN` 查询下规划更稳；单索引场景收益有限；
- 风险：低（一次性统计，耗时随库大小线性）。

## 5.3 P1：候选批量查询（对齐 `batchSearchTerms`）

改动点：`OnsExtractPanel.tryMatchCandidate` 由「一个候选一次查询」改为
「一层内把原形 + 全部还原形一次 `IN` 查询取回，再在内存里按优先级取最长命中」。

- 实测依据：单次 25 值 `IN` 查询 0.13 ms，而 25 次单值查询约 5 ms（每次 0.2 ms 往返）；
- 预期：索引修好后再降 3 - 5 倍（23 ms → 5 - 8 ms）；
- 风险：中（需要重写命中优先级与高亮区间映射逻辑，须回归查词正确性）。

## 5.4 P1：收窄 reading 查询（对齐 `skipReading`）

- 非日语文本（`scope != 'ja'`）或当前词典非日语时不查 reading；
- 单字候选（len == 1）不查 reading —— 假名单字几乎没有词典价值，却占扫描层数的大头。

## 5.5 P2：缓存与数据库参数

- `OnsDeinflector.deinflect()` 结果按字符串做 LRU 缓存（点选同一句时重复率极高）；
- `buildScope()` 结果缓存，仅在词典增删/切换当前词典时失效；
- `PRAGMA cache_size` 提升到 8 - 16 MB（默认约 2 MB，大词典的索引页放不下）；
- 可选：大词典启用 WAL 模式，降低主进程导入与引擎进程查词的跨进程争用
  （需评估 `busy_timeout` 与多进程一致性）。

## 5.6 P2：首次建索引不阻塞

若需为存量库补建大索引，放到后台线程并在 UI 给出「正在优化词典库」状态，
避免首次进入游戏时卡顿。
