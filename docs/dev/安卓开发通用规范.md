# 1. 脚本与工具链

## 1.1 构建产物安装脚本（自动检测设备）

- 状态：按项目落地
- 脚本示例：`scripts/<安装脚本>`
- 规则要点：
  - 自动检测第一台可用设备（可被环境变量覆盖指定）
  - 多 ABI 构建必须显式指定目标 ABI（模拟器经指令转译运行时，缺省可能选错
    ABI 导致启动即链接错误）
  - 提供"先构建再安装"与"安装后拉起"的可选开关
  - 脚本含非 ASCII 文案按 §2.1 编码规则保存

## 1.2 权限一键授予脚本

- 状态：按项目落地
- 脚本示例：`scripts/<授权脚本>`
- 规则要点：
  - 授权范围以项目 Manifest 声明为准，随项目增删
  - 运行时权限用 `pm grant`；特殊权限用 `cmd appops set`
  - 逐项尽力而为不中断：目标 OS 级别低于权限引入版本时自动跳过（该 OS 上
    通常已默认授权）
  - 授权前提：应用已安装（先跑 §1.1）

# 2. 工程与构建

## 2.1 文件编码与 BOM

- 状态：已完成（通用规则，各项目直接采用）
- 规则要点：
  - 含非 ASCII 的 `.ps1` 必须 UTF-8 **带 BOM**（PowerShell 5.1 无 BOM 按 ANSI
    解析，中文乱码甚至语法错误）
  - `.sh` **禁止 BOM**（BOM 三字节破坏 shebang 首行），UTF-8 无 BOM
  - `.bat` 含中文：首行 `@chcp 65001 >nul`，UTF-8 无 BOM
  - 仓库根 `.gitattributes` 固化：`*.sh eol=lf`、`*.ps1/*.bat eol=crlf`、
    二进制 `-text`
  - 保存后核验：`file <脚本>`（看 BOM）或读前 3 字节
  - 工具生成文件时注意：多数语言 `utf-8` 编码**不写 BOM**，需要 BOM 用
    `utf-8-sig`

## 2.2 构建规范

- 状态：按项目落地
- 规则要点：
  - JDK/SDK 版本与路径项目内统一固定（文档或脚本单一来源）
  - 构建命令收敛到文档/脚本单一来源，不散落
  - 磁盘剩余低于阈值（建议 2GB+）禁止构建：构建与模拟器都会写满盘
  - 构建产物属可重建垃圾，纳入清理脚本（见 §4）

## 2.3 提交与文档纪律

- 状态：已完成（通用规则）
- 规则要点：
  - 提交信息 `类型(范围): 摘要`（feat/fix/chore/refactor/docs）
  - 里程碑打注释 tag；不主动 push
  - 会话结束更新进度/记忆/待办三件套

# 3. 运行时与平台

## 3.1 多进程与跨进程

- 状态：待完善
- 已验证要点：
  - 子进程读 SharedPreferences 有陈旧窗口：实时状态走 Intent extra 或文件
    （读时即最新）；跨进程结构化数据用带文件锁的存储（如 SQLite）
  - 全屏原生 surface（游戏/视频）独占合成：宿主 Java UI 走 WindowManager
    悬浮窗承载，且必须显式 `gravity = TOP|START`（缺省 gravity 的 x/y 不按
    左上锚定）
- 待补充：跨进程事件总线规范、进程优先级与保活

## 3.2 JNI / NDK 规范

- 状态：待完善
- 已验证要点：
  - 上行字符串禁止裸 `NewStringUTF`（非法 modified-UTF-8 直接 abort）：
    统一 `NewByteArray` + `new String(bytes, "UTF-8")` 容错解码
  - 非主线程回调：`AttachCurrentThread`/`DetachCurrentThread` 成对；
    每次 JNI 调用后 `ExceptionCheck` 并清除
  - 二进制修改（内联钩子/补丁）：跳板安装前逐条校验被搬指令无 PC 相对编码
    （不满足拒绝挂钩）；代码页 mprotect RW→写→RX→icache 刷新
- 待补充：符号可见性导出清单规范、CMake 目组织约定

## 3.3 资源与多语言

- 状态：待完善
- 已验证要点：多语言目录同步增改（默认语言为文案源）；图标等资源替换须
  覆盖全部密度/形态档位（含自适应图标与单色层）
- 待补充：硬编码文案检查的自动化

## 3.4 模拟器/设备测试

- 状态：待完善
- 已验证要点：
  - 模拟器磁盘预检会失败在 AVD home 所在盘（该盘需预留 2GB+ 余量，

# 4. 测试材料清单（方法框架）

- 状态：已完成（框架）；具体项目材料状态见该项目专门规范文档
- 方法：
  - 材料目录约定：`<测试材料根>/<类别>/`
  - 条目标记（纯文本）：已有真实 ｜ 可生成假测试 ｜ 需用户准备真实 ｜
    建议加入（假测即可覆盖）
  - 按引擎/模块分节，每节列出条目并勾选
  - 区分两类测试项：自动化（长期复用脚本 / 一次性验证）与需人工验证
    （体验类/硬件类/长稳类）
- 生成假测试的判断：能验证"路径与边界"的（空态、损坏输入、编码变体、
  最小工程）用假的；能验证"内容正确性"的（文本/语音/画面对照）用真的

# 5. 测试事项（自动化 vs 手动）

- 状态：按项目落地
- 分类方法：
  - 长期自动化脚本：同一流程手动执行 3 次以上即固化为 `scripts/` 脚本
  - 一次性验证：会话内交互完成，结论记录进度文档，不重复执行
  - 人工验证：体验类（音质/流畅度/节奏）、硬件类（手柄/真机）、长稳类
    （30 分钟+ 连续运行）——列清单由用户执行
